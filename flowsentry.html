FlowSentry

My paper's architecture, taken out of the paper and made to serve requests: a two stage UDP and QUIC attack detector with a request time reject knob, on a connection grouped split that cannot leak. Then I benchmarked it against the simplest baseline I could think of, and it lost, so I published that too.

The result I did not want

A 60 tree forest beats my hierarchy on every axis I care about.

The two stage design exists because a cheap first stage should let you skip expensive QUIC feature extraction on most flows. That is a compute argument, and I had never actually measured it. So I built the benchmark, put four arms in it including the most boring one, and ran it.

artifacts/hierarchy_benchmark.json. Cyan marks the best value in each column, so the cyan row is the winner and the amber row is mine. The quality columns are seeded and reproduce exactly. The two timing columns are one run's snapshot: the artifact's own note says the absolute figures move by tens of percent on a loaded machine and must not be quoted without re-running, while the ratios between arms held across repeats. So the verdict below is stated as a ratio, which is the part that is stable.

One plain forest with 60 trees serves 1.9 times faster, batches 3.5 times faster, has the highest macro F1 of any arm, and beats the hierarchy on binary PR-AUC. No escalation threshold, one model.

The reject knob does not rescue it either, which was my next hope. Any model that emits a probability has a reject knob, and at threshold 0.99 the joint model dominates: it answers 66.6% at 99.41% reliability against the hierarchy's 64.8% at 99.32%. More coverage and more reliability.

What I did about it

ADR 001 now withdraws the compute justification instead of keeping an unmeasured claim, and states what the hierarchy is actually for: it is the paper's architecture, and the escalation rate turns out to be a useful monitoring signal in its own right. QUIC extraction would have to cost more than about 1.9 ms per flow before the design pays for itself, and this implementation does not even defer extraction, so it never could.

Scope it honestly: this is a result about the shipped 25,615 flow sample under one split. It is not a refutation of the paper, which used a different sample, different preprocessing, and a different protocol.

Build

  • A split that cannot leak

    Grouped by the UDP 5-tuple connection, so no connection has flows in both training and test. A random split would score higher and mean less.

    metrics.json : split, n_train 19045, n_test 6570

  • The reject knob as a request parameter

    The threshold is set per request, not baked into the model, so an operator can move their operating point without a redeploy. Interactive version on the front page.

  • A service, containerised, with CI

    FastAPI for prediction and for the curve, a Streamlit dashboard with the live knob, a Dockerfile, and GitHub Actions running ruff and pytest. There is no public deploy with a URL yet, and the repo's roadmap says so rather than implying otherwise.

  • Reproduces byte for byte from a cold clone

    python scripts/reproduce.py retrains from the committed sample and fails loudly if metrics.json changes by a single byte. Verified from a fresh clone and a fresh virtual environment.

  • Eight ADRs that name what was rejected

    Including the one that withdrew its own claim. Plus a model card and a threat model, because a detector without a stated adversary is a classifier with a security word in front of it.

Weak spots

Stated here rather than waiting to be found.

  • The numbers are on a 25,615 flow sample, not the full dataset

    A deliberate choice so a cold clone reproduces without a multi gigabyte download. The README says so on the first screen.

  • 0.977 is attack detection, not family attribution

    Per class PR-AUC runs from 0.9986 on the dominant class down to 0.0424 on the rarest. Fine grained attribution on a 3,700 to 1 imbalance is not solved here, and the knob is how the system declines instead of guessing.

    metrics.json : per_class_pr_auc

  • It is not deployed anywhere public

    Containerised and CI tested, but there is no live URL. Until there is, I say "built and shipped", not "deployed".
